# Final correctness work

## Frontend: manual DST fall-overlap selection

- **Decision:** Resolve a manually entered ordinary-note wall time in the profile IANA timezone. A spring-forward gap fails the wall-clock round trip and remains a field-level error. A fall-back overlap renders a named radio group with both chronological occurrences, their explicit UTC offsets, and their UTC clock times. Neither option is preselected. Save is blocked until the user chooses one, and the chosen offset-qualified instant is sent unchanged to the API.
- **Alternative considered:** Continue selecting the earlier occurrence automatically. This matches recurring-series generation, but it cannot express the user’s intent for a one-off note and violates the manual-entry rule. A browser-zone `Date` conversion was also rejected because the browser zone can differ from the saved profile zone.
- **Scope boundary:** Recurring schedules keep the frozen rule that ambiguous generated occurrences select the earlier instant. Calendar drag values already carry an offset and are not ambiguous manual wall-time input.
- **Evidence:** `note-form.test.tsx` covers the Budapest 2026 spring gap, both fall-overlap candidates, accessible group/radio names, no default selection, blocked submit, explicit second-occurrence selection, and the `+01:00` request payload. The full frontend suite passes (30 tests), as do TypeScript typecheck and production build. The build retains the known main-chunk warning (795.00 kB minified); this change adds no dependency.


## Backend: atomic recurrence splits and purged tombstones

- **Decision:** Validate the complete generated successor schedule before creating the successor series. Reject generated instants at or before the request-time `now` with `409 historical_replacement`. Reject instants that match either the stable recurrence key or the effective `starts_at` of any non-superseded predecessor row before the split boundary with `409 recurrence_collision`. This includes deleted and purged predecessor history.
- **Decision:** A purged recurrence row is an irreversible redacted tombstone. A split never reuses its note identity or clears its purge marker. The old row is superseded, its minimal `cancelled=true` / empty-fields occurrence exception stays on the predecessor for audit, and the successor gets a new, editable note identity. All list, trash, calendar, upcoming, detail, and mutation paths exclude purged identities.
- **Alternatives rejected:** Reusing the purged row would expose it from list/calendar while detail and edit still returned 404, and would violate permanent purge. Deleting every old exception would erase the required cancellation marker. Checking only original recurrence keys would miss an earlier overridden note dragged onto a generated successor instant.
- **Evidence:** PostgreSQL HTTP integration regressions cover stable-key and effective-time collisions, generated historical instants, atomic unchanged lineage/note counts after rejection, real purge followed by split, old tombstone and cancellation-marker retention, new identity visibility in list/calendar/detail, old identity exclusion from normal/trash/detail/edit, and successful edit of the replacement.
